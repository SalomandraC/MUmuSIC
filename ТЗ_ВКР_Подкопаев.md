## 1. Назначение и цели создания приложения

### 1.1 Назначение программного обеспечения

**[С]** Программное обеспечение представляет собой мобильное приложение (Flutter) в сочетании с серверным API (Node.js/TypeScript, PostgreSQL), предназначенное для работы с персональной фонотекой пользователя: поиска аудиоматериалов, сохранения треков на сервере, организации их в плейлисты и избранное, а также синхронизации между устройством и сервером.

**[С]** В текущей версии источником аудиоматериалов выступают: (а) 30-секундные превью-фрагменты каталога iTunes (поиск по externally available iTunes Search API), загружаемые на устройство для офлайн-прослушивания; (б) файлы аудиоформата, загружаемые самим пользователем в собственное хранилище аккаунта через `POST /tracks` (multipart).

**[П]** Назначение расширяется: приложение становится клиентом серверного конвейера анализа и трансформации аудио. По запросу пользователя сервер выполняет над файлом одну или несколько ML-операций — автоматическую транскрипцию с покадровой/пословной временной привязкой (Whisper), разделение на независимые дорожки-стемы (Demucs: вокал, барабаны, бас, прочее), расчёт метаакустических признаков (темп, тональность, громкость) — и возвращает результат в виде связанных с треком артефактов, воспроизводимых и отображаемых на клиенте.

**[П]** Итоговая формулировка назначения для пояснительной записки: *автоматизированный сбор, хранение, машинный анализ и вторичное использование пользовательского аудиоконтента в рамках единого мобильно-серверного комплекса с измеримыми показателями качества анализа.*

### 1.2 Цели создания системы

Основными целями создания системы являются:

1. **[С]** Обеспечение сквозного жизненного цикла аудиотрека на мобильном клиенте: поиск → предпросмотр → сохранение → организация в плейлисты/избранное → офлайн-воспроизведение.
2. **[С]** Реализация аутентификации и авторизации на базе JWT (пары access/refresh-токенов, bcrypt-хэширование паролей) с поддержкой гостевого режима и последующей «конверсацией» гостевого аккаунта в полноценный.
3. **[С]** Реализация серверного хранилища треков с раздачей файлов по HTTP-диапазонам (Range/206) и модуля синхронизации пользовательских плейлистов между устройством и БД.
4. **[С]** Реализация экрана топ-чартов на данных собственного сервера (агрегированная публичная выборка треков) с пагинацией и детализацией.
5. **[Д]** Приведение клиентской части к единому архитектурному слою: в текущей версии feature-модуль `home/` реализован по «чистой архитектуре» (domain / repository / usecase / presentation), тогда как `search/`, `playlists/`, `favorites/`, `storage/` содержат только `presentation/`, обращающийся к HTTP-клиенту напрямую. Целевое состояние — единая схема для всех модулей.
6. **[П]** Разработка серверного асинхронного конвейера обработки аудио, пригодного для выполнения длительных ML-задач без блокировки HTTP-запроса: очередь задач, статусы, прогресс, пул воркеров, хранение артефактов.
7. **[П]** Интеграция модели распознавания речи Whisper с выдачей текста со сквозной временной привязкой на уровне слов и последующим отображением на клиенте в виде синхронизированного текста.
8. **[П]** Интеграция модели разделения музыкальных сигналов Demucs с сохранением четырёх независимых дорожек и их пооперационным воспроизведением на клиенте (регулируемая громкость каждой стемы, отключение вокала/барабанов).
9. **[П]** Проведение экспериментальной оценки конвейера: измерение точности транскрипции (WER), качества разделения (SDR/SIR), времени обработки и потребления памяти при различных конфигурациях моделей; сопоставление серверного инференса с локальным (on-device) по latency/точности/энергопотреблению.
10. **[П]** Создание прототипа, пригодного как основа для дальнейшей разработки сервисов анализа аудиоконтента (репетиционные и караоке-сценарии, доступность контента для людей с нарушениями слуха через визуализацию текста).

## 2. Характеристики объекта автоматизации

Объектами автоматизации являются:

**[С]** процессы поиска аудиоматериалов во внешнем каталоге (iTunes Search API) с нормализацией ответа к внутреннему формату `TrackDto` и кэшированием результатов на устройстве;

**[С]** процессы загрузки и сохранения аудиофайлов пользователя на сервере, включая контроль размера и MIME-типа, генерацию пути в хранилище и регистрацию метаданных в реляционной БД;

**[С]** процессы аутентификации, продления сессии (refresh-поток) и разграничения доступа на уровне владельца ресурса;

**[С]** процессы локального хранения состояния приложения (Hive: тема, язык, флаг гостевого режима, учётные данные, базовый URL API, токены) и защищённого хранения токенов (`flutter_secure_storage`);

**[С]** процессы синхронизации структуры плейлистов между устройством и сервером (полная выгрузка/загрузка JSON-представления пользовательских данных);

**[П]** процессы машинной обработки аудио: декодирование в PCM, подача на вход модели ASR и модели разделения, постобработка (нормализация громкости по EBU R128, расчёт темпа и тональности, перекодирование в целевые форматы), сборка артефактов;

**[П]** процессы управления долгоживущими задачами: постановка в очередь, планирование, исполнение воркером, фиксация прогресса и результата, обработка отказа с повтором, инвалидация артефактов при удалении исходного трека;

**[П]** процессы доставки результата на клиент: опрос статуса задачи, push-уведомление о завершении, догрузка артефактов и их офлайн-кэширование;

**[П]** процессы ведения журнала обработки с измеримыми показателями (длительность этапа, устройство исполнения CPU/GPU, объём входа и выхода), необходимыми для экспериментальной части ВКР;

**[С]** процессы взаимодействия с метками NFC (чтение/запись технологического формата, фильтрация по `nfc_tech_filter`) — вспомогательная демонстрационная функция мобильного клиента.

## 3. Требования к видам обеспечения

### 3.1 Требования к информационному обеспечению

**[С] Классы решаемых задач:** поиск и предпросмотр аудиозаписей, персональное хранение фонограмм, структурирование (плейлисты, избранное), синхронизация, агрегирование публичных топ-чартов, аутентификация и гостевой доступ.

**[П] Классы решаемых задач (расширение):** распознавание речи, разделение музыкальных сигналов, извлечение акустических признаков, семантический поиск по похожести.

**[С] Основные информационные сущности текущей БД:**

| Сущность | Назначение | Ключевые атрибуты |
|---|---|---|
| `users` | Учётная запись | id, username, email, password_hash, role, guest_session_id, created_at, updated_at |
| `tracks` | Фонограмма и её метаданные | id, user_id, title, artist, album, duration, file_path, file_format, file_size, notes, is_public, created_at |
| плейлисты (`sync`) | Структура пользовательских плейлистов | сериализованное представление, привязка к user_id |
| топ-чарты | Публичная выборка треков | id, агрегирующие поля, признак активности |

**[П] Новые информационные сущности конвейера обработки:**

| Сущность | Назначение | Ключевые атрибуты |
|---|---|---|
| `processing_jobs` | Задача ML-обработки | id, track_id, type (`transcribe` \| `separate` \| `analyze`), status (queued/running/succeeded/failed/cancelled), model_version, priority, attempts, progress, error_code, created_at, started_at, finished_at |
| `audio_artifacts` | Результат обработки | id, job_id, track_id, kind (stem_vocals / stem_drums / stem_bass / stem_other / transcript / waveform / embedding), object_key, mime_type, size_bytes, duration_ms, created_at |
| `transcripts` | Расшифровка | artifact_id, language, model_name, wer_estimate, segments JSONB (`{start, end, text}`), words JSONB (`{word, start, end}`) |
| `audio_features` | Метаакустические признаки | track_id, bpm, musical_key, loudness_lufs, duration, silence_ratio, energy_profile |
| `track_embeddings` | Векторы похожести | track_id, model_name, embedding `vector(n)` (pgvector), индекс по схожести |

**[С]** Форматы обмена между клиентом и сервером — JSON (UTF-8) поверх HTTP/1.1; бинарная передача аудио — multipart/form-data при загрузке и потоковая выдача со статусом 206 Partial Content при скачивании.

**[П]** Форматы представления результатов: аудио — WAV (PCM 44,1 кГц, промежуточный) и AAC/Opus/M4A (итоговый, для стемов); текстовый слой транскрипции — JSON с покадровыми интервалами; внутренний формат времени — миллисекунды с начала файла. Формат `transcripts.words` должен обеспечивать синхронное выделение слов при воспроизведении (допустимое смещение маркировки — не более 200 мс).

**[С]** Идентификация файлов в хранилище — детерминированный ключ на основе владельца и содержимого, исключающий коллизии и доступ по чужому пути. **[Д]** В текущей версии каталог `/storage` раздаётся статикой без проверки подлинности, то есть идентификатор файла фактически является паролем; целевое состояние — выдача через авторизованный контроллер либо краткоживущие подписанные URL.

**[П]** Централизованное объектное хранилище (S3-совместимое: MinIO/Supabase Storage/облако провайдера) вместо локального каталога файловой системы — обязательное условие работы нескольких воркеров и горизонтального масштабирования.

**[П]** Миграционное сопровождение схемы БД: версионированные SQL-миграции в репозитории, воспроизводимое развёртывание «с нуля». **[Д]** В текущей версии схема существует только в SQL-запросах слоя репозиториев, миграции отсутствуют.

### 3.2 Требования к применению языков программирования

**Мобильный клиент:**
- **[С]** Dart (версия 3.x, SDK `>=3.0.0 <4.0.0`), фреймворк Flutter; роутинг — go_router; состояние — провайдеры с ручной композицией в `di/dependency_injection.dart`; локальное хранение — Hive; защищённое хранение — flutter_secure_storage; воспроизведение — just_audio; сетевой доступ — http; NFC — flutter_nfc_kit; разрешения — permission_handler; конфигурация окружения — flutter_dotenv.
- **[С]** Kotlin (Android-обёртка `MainActivity.kt`) и Swift (iOS `AppDelegate.swift`) — только платформенные хосты.
- **[П]** Целевое изменение: переход на декларируемый контейнер зависимостей и единый слой состояния (Riverpod или BLoC) — как предмет архитектурного обоснования в работе.

**Серверное API (оркестрация):**
- **[С]** TypeScript 5.x, среда выполнения Node.js 18/20+, веб-фреймворк Express 4.x; валидация входных данных — Zod; аутентификация — jsonwebtoken, bcrypt; загрузка файлов — multer; документация API — Swagger/OpenAPI (swagger-jsdoc + swagger-ui-express); доступ к БД — драйвер `postgres`; логирование — morgan; тесты — Jest + ts-jest.
- **[Д]** Требуется устранение дублирования: в репозитории сосуществуют legacy-сервер (`server/`, сессионная аутентификация через express-session, плоская структура routes) и целевой сервер (`backend/`, модульная структура + JWT). Целевое состояние — единственный серверный модуль, legacy удаляется.
- **[Д]** Требуется удаление из зависимостей неиспользуемого клиента `@supabase/supabase-js` либо его переход в основной стек хранения (решение фиксируется в тексте работы).

**Сервис машинного обучения (новый компонент):**
- **[П]** Python 3.10–3.12. Библиотеки: PyTorch 2.x; разделение — `demucs` (реализация htdemucs / htdemucs_ft); распознавание речи — `faster-whisper` (CTranslate2-бэкенд) либо `whisper` с квантизацией; аудио-I/O и декодирование — `ffmpeg`, `torchaudio`/`soundfile`; признаки — `librosa` или `essentia`; метрики оценки — `sclite`/`jiwer` (WER), `asteroid`/`mmdseval` (SDR).
- **[П]** Межпроцессное взаимодействие — только через очередь задач и объектное хранилище; прямого вызова Python из Node не допускается.

- **[С]** Среда выполнения: Node.js 18+, npm; PostgreSQL 14+.

- **[П]** Непрерывная интеграция: конвейер сборки и тестирования (GitHub Actions/GitLab CI) — сборка TS, сборка Flutter (release APK в артефакты), прогон миграций на тестовой БД, запуск тестов, сбор метрик покрытия. **[Д]** В текущей версии CI отсутствует полностью.

### 3.4 Требования к аппаратному обеспечению

**Серверная часть (минимальная конфигурация для демонстрации):**
- Процессор: 4 ядра / 8 потоков, 2.5 ГГц и выше.
- Оперативная память: 16 ГБ (CPU-вариант), 32 ГБ (GPU-вариант).
- Графическая подсистема: NVIDIA GPU с объёмом памяти от 6 ГБ (вариант `htdemucs_mb` + `faster-whisper` small/`int8`) либо от 10 ГБ (вариант `htdemucs_ft` + `large-v3`).
- Дисковое пространство: 100 ГБ SSD, из них до 15 ГБ — веса моделей, до 60 ГБ — контрольная коллекция фонограмм и артефакты.
- Сетевое подключение: не менее 100 Мбит/с на приём и отдачу.

**Серверная часть (целевая конфигурация):**
- CPU: 8 ядер; RAM: 32–64 ГБ; GPU: NVIDIA RTX 3090/4090 (24 ГБ) или облачный эквивалент; NVMe 500 ГБ; канал 1 Гбит/с; до 4 одновременных воркеров обработки.

**Клиентская часть:**
- **[С]** Смартфон Android API 23+ / iOS 12+, RAM от 3 ГБ, свободное хранилище от 2 ГБ (офлайн-кэш превью и загруженных треков), NFC — опционально для демонстрационной функции.
- **[С]** Сетевой доступ не менее 5 Мбит/с для загрузки фонограмм; работа ключевых экранов (библиотека, плейлисты, избранное, настройки) должна сохраняться без сети на локальном кэше.
- **[П]** Для сравнительного эксперимента по on-device инференсу: устройство с чипсетом уровня Snapdragon 7-й серии / Apple A14 и выше.

### 3.5 Требования к совместимости и интеграции

- **[С]** Обратная совместимость API-контрактов с уже выпущенными сборками клиента (версия приложения 1.0.1+2): изменение формы ответа допускается только через версионирование пути (`/v1`) или добавление необязательных полей.
- **[П]** Конвейер обработки не должен изменять существующие эндпоинты `auth`, `tracks`, `sync`, `top-charts`; ML-функциональность выносится в отдельные пространства `/jobs`, `/artifacts`, `/analysis`.
- **[П]** Совместимость форматов входных файлов: MP3, M4A/AAC, WAV, FLAC, OGG; при недопустимом входном формате задача завершается с различимым кодом ошибки, а не с зависанием.

## 4. Дополнительные требования

### 4.1 Требования к хостингу и инфраструктуре

- **[С]** Обеспечение доступности сервиса на уровне не менее 70 % (базовое требование исходного ТЗ, выполняется текущим стендом).
- **[П]** Целевой уровень доступности API — не менее 95 % в месячном измерении для демонстрационного контура; деградация сервиса ML-обработки не должна влиять на доступность базовых эндпоинтов (при остановленном воркере задачи остаются в состоянии `queued`, а не завершаются ошибкой).
- **[П]** Наличие системы автоматического оповещения о сбоях: уведомление при падении воркера, при времени задачи сверх лимита (для транскрипции — 10 мин, для разделения — 15 мин), при заполнении хранилища свыше 80 %.
- **[П]** Разделение контуров: локальный (docker-compose, полностью воспроизводимый для защиты), стендовый (публичный доступ для комиссии) — с идентичными миграциями и конфигурацией через переменные окружения.
- **[Д]** Требования к инфраструктуре репозитория: вывести из-под версионного контроля `node_modules`, `dist`, `coverage`, а также медиафайлы; исключить хранение `.env` с реальными значениями секретов (в текущей версии `backend/.env` и `server/.env` отслеживаются git'ом, что требует ротации ключей); предоставить `.env.example` с описанием переменных.

### 4.2 Требования к защите данных и обеспечению безопасности

- **[С]** Хэширование паролей bcrypt (стоимость по умолчанию библиотеки); неразглашение `password_hash` в ответах (сущность `UserSafe`).
- **[С]** Раздельные секреты и типизация access/refresh-токенов: токен содержит обязательное поле `type`, проверляется на совпадение с ожидаемым типом.
- **[С]** Валидация всех входных данных контроллеров через Zod-схемы; централизованная обработка ошибок с сопоставлением кодов HTTP.
- **[С]** CORS-белый список origin'ов, отключающий междоменные запросы из неизвестных источников в продуктивной среде.
- **[П]** Отзыв токенов: реализовать проверку `tokenVersion` (закладывается в JWT, но в текущей версии нигде не верифицируется), что обеспечит инвалидацию refresh-токенов при выходе из системы и смене пароля; хранить состояние отзыва в БД.
- **[П]** Авторизация доступа к медиа: выдача файлов только через проверку владельца либо подписанные URL с ограниченным сроком действия; запрет публичного доступа к чужим фонограммам независимо от значения `is_public`.
- **[П]** Ограничение частоты и объёма загрузки (rate limit, максимальный размер файла, квота на аккаунт), в том числе для предотвращения DoS через постановку тяжёлых ML-задач.
- **[П]** Приоритет очередей и справедливое планирование: не более N задач одновременно на одного пользователя.
- **[П]** Проксирование внешних запросов (iTunes Search API) через сервер при необходимости, чтобы клиент не зависел от изменений внешнего каталога.
- **[П]** Правовые ограничения: в финальной версии объектом обработки заявляются исключительно фонограммы, загруженные самим пользователем; превью iTunes (30 с) используются только как предпросмотр и не подлежат серверной ML-обработке и вторичному публичному размещению. Поля `is_public` и публичные топ-чарты допускают только контент, явно опубликованный владельцем.

- **[С]** Модульное тестирование логики валидации, хэширования, работы с токенами, утилит массивов (сервер); локального хранилища, парсеров внешнего каталога, доменных usecase (клиент).

## 7. Ограничения и допущения

1. **[П]** Ресурс GPU не гарантируется: при его отсутствии допускается вариант с квантованными моделями (`htdemucs_mb`, `faster-whisper` small/int8) с обязательной отметкой о влиянии на метрики в тексте работы; в крайнем варианте сохраняется только этап распознавания речи.
2. **[Д]** Внешний каталог (iTunes Search API) не является частью работы и может изменить недоступность формата ответа; серверная схема хранения не должна от него зависеть.
3. **[П]** Разрешение прав на использование моделей: Whisper — MIT, Demucs — MIT; используемые предобученные веса применяются без дообучения; дообучение не входит в объём работ и указывается как направление дальнейшего развития.
4. **[П]** Контрольная аудиовыборка для экспериментов формируется из свободнораспространяемых записей с целью исключения претензий по авторским правам при публичной демонстрации.
5. **[П]** Срок выполнения: этапы 1–3 являются блокирующими и должны быть завершены до начала вычислительных экспериментов, поскольку изменение схемы хранения и появление очереди задач меняют методику замеров.
