# 5. ОСНОВНЫЕ ТЕХНИЧЕСКИЕ РЕШЕНИЯ

## 5.1. Решения по структуре системы, подсистем, средствам и способам связи для информационного обмена между компонентами системы

Система построена по модульной архитектуре с разделением на функциональные модули, каждый из которых реализует определённую область функциональности приложения. Архитектура приложения следует принципам Clean Architecture с разделением на слои: domain (доменный слой), presentation (слой представления) и core (базовый слой). Модули системы включают: модуль управления состоянием приложения (app), модуль аутентификации (auth), модуль главного экрана и работы с сетью (home), модуль работы с гостевыми треками (guest_tracks), модуль работы с NFC (nfc), модуль настроек (settings) и модуль темизации (theme).

Информационный обмен между компонентами системы осуществляется через механизм управления состоянием на основе паттерна Provider с использованием `ChangeNotifier` и `InheritedNotifier`. Глобальное состояние приложения управляется через `AppModel`, который уведомляет подписчиков об изменениях через механизм `notifyListeners()`. Компоненты пользовательского интерфейса подписываются на изменения состояния через `ListenableBuilder`, что обеспечивает реактивное обновление интерфейса при изменении данных. Связь между слоями domain и presentation осуществляется через интерфейсы репозиториев и use cases, что обеспечивает разделение бизнес-логики и логики представления.

Навигация между экранами приложения реализована через библиотеку go_router, которая обеспечивает декларативное определение маршрутов и централизованное управление переходами. Маршрутизация включает правила перенаправления на основе статуса авторизации пользователя, что обеспечивает контроль доступа к различным разделам приложения.

## 5.2. Решения по взаимосвязям АС со смежными системами, обеспечению её совместимости

Приложение взаимодействует с внешними системами через HTTP-протокол для получения данных и выполнения операций. Основными смежными системами являются публичный API сервиса iTunes для поиска музыкальных треков и внешний сервер для получения списка гостевых треков. Взаимодействие с iTunes API осуществляется через REST-интерфейс с использованием HTTP GET-запросов, данные передаются в формате JSON. Взаимодействие с сервером гостевых треков также реализовано через REST API с поддержкой настройки базового URL через интерфейс настроек приложения.

Обеспечение совместимости с различными версиями операционных систем реализовано через использование кроссплатформенного фреймворка Flutter, который обеспечивает единообразное поведение приложения на платформах Android и iOS. Для работы с разрешениями системы используется библиотека permission_handler, которая автоматически адаптируется к версии операционной системы и запрашивает соответствующие разрешения (для Android 13+ используется READ_MEDIA_AUDIO, для более старых версий – WRITE_EXTERNAL_STORAGE).

Совместимость с различными устройствами обеспечивается через адаптивный дизайн интерфейса, который автоматически подстраивается под размер экрана и ориентацию устройства. Приложение поддерживает работу в портретной и альбомной ориентациях с автоматической адаптацией компонентов интерфейса.

## 5.3. Решения по режимам функционирования, диагностированию работы системы

Приложение функционирует в двух основных режимах: режиме авторизованного пользователя и гостевом режиме. Режим работы определяется при инициализации приложения на основе данных, сохранённых в локальном хранилище. В гостевом режиме пользователю доступны базовые функции (поиск треков в сети, работа с NFC, настройки), в то время как авторизованным пользователям предоставляется расширенный набор функций.

Диагностирование работы системы реализовано через механизм логирования с использованием `debugPrint()`, который выводит информацию о состоянии системы, выполняемых операциях и возникающих ошибках. Логирование включает информацию о сетевых запросах (URL, статус ответа, время выполнения), состоянии аудиоплеера, операциях с базой данных и навигационных переходах. В процессе разработки логирование позволяет отслеживать выполнение операций и выявлять проблемы, в то время как в production-версии уровень логирования может быть снижен для оптимизации производительности.

Обработка ошибок реализована через механизм try-catch блоков с отображением пользователю информативных сообщений об ошибках через SnackBar. Для сетевых операций реализована обработка таймаутов и ошибок подключения с предоставлением пользователю возможности повторить операцию.

## 5.4. Решения по численности, квалификации и функциям персонала АС, режимам его работы, порядку взаимодействия

Приложение предназначено для использования конечными пользователями без необходимости привлечения специального персонала для его эксплуатации. Пользователи приложения могут быть разделены на две категории: авторизованные пользователи, имеющие полный доступ к функциям приложения, и гостевые пользователи, использующие ограниченный набор функций без регистрации.

Режим работы пользователя определяется при входе в приложение: пользователь может выполнить авторизацию, зарегистрироваться или войти в гостевом режиме. Взаимодействие пользователя с системой осуществляется через интуитивно понятный пользовательский интерфейс, не требующий специальной подготовки. Все функции приложения доступны через навигационное меню и экраны приложения, что обеспечивает простоту использования.

Для администраторов системы (разработчиков) предусмотрены функции диагностики и настройки через экран настроек, включающий возможность тестирования подключения к бэкенду, настройки параметров API и просмотра информации о состоянии системы.

## 5.5. Сведения об обеспечении заданных в техническом задании потребительских характеристик системы, определяющих её качество

Приложение обеспечивает высокое качество пользовательского опыта через реализацию современного интерфейса, соответствующего принципам Material Design, что обеспечивает интуитивность использования и визуальную привлекательность. Производительность приложения оптимизирована через использование механизма debouncing для поисковых запросов, кэширование данных в локальном хранилище и асинхронную загрузку данных, что обеспечивает отзывчивость интерфейса.

Надёжность системы обеспечивается через обработку ошибок на всех уровнях приложения, валидацию входных данных, проверку доступности сетевых ресурсов и обработку исключительных ситуаций. Безопасность данных пользователя обеспечивается через локальное хранение конфиденциальной информации в зашифрованном хранилище Hive и безопасную передачу данных через HTTPS-протокол при взаимодействии с внешними сервисами.

Масштабируемость системы обеспечивается через модульную архитектуру, которая позволяет добавлять новые функциональные модули без изменения существующего кода. Поддерживаемость кода обеспечивается через следование принципам Clean Architecture, использование единообразных паттернов проектирования и документирование кода.

## 5.6. Состав функций, комплексов задач (задач), реализуемых системой

Система реализует следующий состав функций:

**Функции аутентификации и управления пользователями:**
- Вход в систему с использованием email и пароля
- Регистрация новых пользователей с указанием никнейма
- Вход в гостевом режиме без регистрации
- Выход из аккаунта с очисткой данных сессии
- Управление состоянием авторизации и сохранение сессии

**Функции поиска и работы с музыкальными треками:**
- Поиск треков через iTunes API с автоматическим debouncing
- Отображение результатов поиска с обложками и метаданными
- Предпрослушивание треков через previewUrl
- Скачивание треков на локальное хранилище устройства
- Загрузка списка гостевых треков с внешнего сервера
- Воспроизведение треков через аудиоплеер

**Функции управления воспроизведением:**
- Воспроизведение, пауза и остановка треков
- Изменение скорости воспроизведения (0.5x, 1.0x, 1.5x, 2.0x)
- Перемотка трека через прогресс-бар
- Отображение текущей позиции и длительности трека
- Управление воспроизведением из списка треков

**Функции работы с NFC:**
- Чтение данных с NFC-меток
- Обработка прочитанной информации
- Интеграция с системой воспроизведения треков

**Функции управления настройками:**
- Переключение между светлой и тёмной темами оформления
- Настройка параметров подключения к API серверу
- Тестирование подключения к бэкенду
- Поделиться приложением
- Связь с поддержкой
- Просмотр пользовательского соглашения

**Функции навигации:**
- Переход между экранами приложения
- Управление доступом к экранам на основе статуса авторизации
- Возврат на предыдущий экран

## 5.7. Решения по комплексу технических средств, его размещению на объекте

Приложение разработано для работы на мобильных устройствах с операционными системами Android и iOS. Минимальные требования к техническим средствам определяются требованиями платформы Flutter: для Android требуется версия Android 4.1 (API level 16) и выше, для iOS требуется версия iOS 11.0 и выше. Приложение оптимизировано для работы на устройствах с различными размерами экранов: от смартфонов с небольшими экранами до планшетов.

Размещение приложения на устройстве пользователя осуществляется через установку из магазина приложений (Google Play для Android, App Store для iOS) или через установку APK-файла для Android. После установки приложение размещается в системной директории приложений устройства, а данные пользователя сохраняются в локальном хранилище устройства: для Android используется директория приложения в `/data/data/`, для iOS – директория Documents приложения.

Для работы приложения требуется доступ к интернету для взаимодействия с внешними API (iTunes API, сервер гостевых треков). При отсутствии интернет-соединения приложение продолжает работу с ограниченным функционалом: доступны сохранённые настройки и локальные данные, но недоступны функции поиска треков и загрузки данных с сервера.

## 5.8. Решения по составу информации, объёму, способам её организации, видам машинных носителей, входным и выходным документам и сообщениям, последовательности обработки информации

Информация в системе организована в виде структурированных данных, хранящихся в локальной базе данных Hive и передаваемых через сетевые API в формате JSON. Локальное хранилище содержит следующие типы данных: состояние приложения (тема, язык, статус авторизации), данные пользователя (email, никнейм, режим работы), настройки подключения (базовый URL API сервера).

Данные о музыкальных треках передаются в формате JSON и включают следующие поля: идентификатор трека, название, исполнитель, длительность, URL обложки, URL превью или потокового воспроизведения. Объём передаваемых данных оптимизирован через передачу только необходимых полей и использование сжатия данных на уровне HTTP-протокола.

Входными данными системы являются: данные аутентификации (email, пароль, никнейм), поисковые запросы пользователя, команды управления воспроизведением, данные с NFC-меток, настройки приложения. Выходными данными являются: списки найденных треков, аудиопотоки для воспроизведения, скачанные аудиофайлы, уведомления пользователю о состоянии операций.

Последовательность обработки информации: при вводе поискового запроса выполняется валидация данных, затем формируется HTTP-запрос к API, полученный ответ десериализуется из JSON, данные преобразуются в модели домена, после чего отображаются в пользовательском интерфейсе. При выборе трека для воспроизведения извлекается URL аудиофайла, выполняется загрузка и буферизация данных, после чего начинается воспроизведение.

## 5.9. Решения по составу программных средств, языкам деятельности, алгоритмам процедур и операций и методам их реализации

Программные средства системы разработаны на языке программирования Dart версии 3.0.0 и выше с использованием фреймворка Flutter для создания пользовательского интерфейса. Основные библиотеки и зависимости включают: hive_flutter для локального хранилища, go_router для навигации, just_audio для воспроизведения аудио, http для сетевых запросов, permission_handler для работы с разрешениями системы, flutter_nfc_kit для работы с NFC.

Архитектура приложения следует принципам Clean Architecture с разделением на слои: domain слой содержит бизнес-логику и модели данных, presentation слой содержит пользовательский интерфейс и логику представления, core слой содержит базовые компоненты, используемые во всём приложении. Управление состоянием реализовано через паттерн Provider с использованием ChangeNotifier для реактивного обновления интерфейса.

Алгоритмы процедур и операций реализованы через use cases в domain слое, которые инкапсулируют бизнес-логику для выполнения конкретных задач. Репозитории обеспечивают абстракцию доступа к данным и реализуют паттерн Repository для разделения логики работы с данными и бизнес-логики. Методы реализации включают асинхронное выполнение операций через Future и Stream для обработки потоков данных, что обеспечивает неблокирующее выполнение операций и отзывчивость интерфейса.

Обработка ошибок реализована через механизм исключений с использованием try-catch блоков и предоставлением пользователю информативных сообщений об ошибках. Валидация данных выполняется на уровне пользовательского интерфейса через встроенные валидаторы Flutter и на уровне бизнес-логики через проверки в use cases.
