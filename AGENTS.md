# Памятка по репозиторию MUmuSIC

## Ориентация

- Начните с `README.md`, `docs/ARCHITECTURE.md` и `docs/DEVELOPMENT.md`.
- Клиент: `tier-maker/tiermaker/` (Flutter, package `mumusic`).
- Для новых серверных задач исходная точка — `backend-java/` (Java 21, Spring MVC, JDBC, Flyway), если задача не указывает другую реализацию.
- `backend/` — предыдущий Express/TypeScript API; `server/` — ещё более старый сервер. При этом `server/storage/` остаётся действующим общим хранилищем.
- ТЗ содержит реализованные функции, долг и планы. Не описывайте Whisper/Demucs и очередь задач как существующие компоненты без подтверждения кодом.

## Работа с изменениями

- Сначала проверьте рабочее дерево и сохраните чужие незакоммиченные изменения.
- Следуйте реальному пути вызовов: Flutter сочетает feature-модули, общие data/domain-слои и прямые обращения к API из экранов.
- Основная конфигурация маршрутов Flutter — `lib/core/navigation/app_router.dart`, подключённая из `lib/app/my_app.dart`.
- При изменении API согласуйте клиент и сервер: JSON-поля, статусы ошибок, даты, строковый `file_size`, JWT и подписанные ссылки влияют на совместимость.
- Добавляйте новые миграции для новых изменений схемы; учитывайте, что Java и Node могут использовать одну БД. Не запускайте миграции против неизвестного окружения.
- Не меняйте и не удаляйте `server/storage/` как временный или устаревший каталог. Не удаляйте Docker-том БД ради обычного перезапуска.
- Не коммитьте `.env`, токены или секреты. Используйте `.env.example`; клиентский `.env` попадает в приложение как asset и содержит только публичную конфигурацию.
- Не редактируйте генерируемые `build/`, `dist/`, `.dart_tool/`, `target/` вместо исходников.

## Проверки

- Flutter: из `tier-maker/tiermaker/` — `flutter analyze`, `flutter test`; при платформенных изменениях сборка для нужной платформы.
- Java: из `backend-java/` — `mvn test`; `mvn package` для проверки сборки.
- Node: из `backend/` — `npm test -- --runInBand`, `npm run build` (зависимости устанавливаются через `npm ci`).
- Для документационных изменений достаточно сверить команды, пути и ссылки с репозиторием.
- В итоговом сообщении перечисляйте реально выполненные проверки и ограничения. Не переносите исторические заявления о количестве тестов и совместимости в результат текущей проверки.

Поддерживайте документацию на русском языке и обновляйте карту проекта при изменении структуры или сценариев запуска.
