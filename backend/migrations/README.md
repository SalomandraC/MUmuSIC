# Миграции базы данных

Схема БД теперь хранится в репозитории: `backend/migrations/NNNN_name.sql`.
Чистую базу можно развернуть одной командой, без ручного восстановления по запросам.

| Файл | Что делает |
|---|---|
| `0001_initial_schema.sql` | таблицы `users`, `tracks`, `playlists`, `playlist_tracks`, `guest_tracks` |
| `0002_indexes.sql` | уникальность email/username без учёта регистра и индексы под запросы сервера |

Запускает их `server/db/migrate.ts`. Это небольшой раннер на той же библиотеке `postgres`,
что и сервер, новых зависимостей нет. Строка подключения берётся из `DATABASE_URL` в `backend/.env`.

## Команды

```bash
npm run migrate                      # применить все новые миграции
npm run migrate:status               # что применено, что ожидает, что изменено
npm run migrate:new -- add_track_mood   # создать 0003_add_track_mood.sql
npm run migrate:baseline -- 0001     # отметить миграции до 0001 как уже применённые
npm run migrate:prod                 # то же, что migrate, но из собранного dist (после npm run build)
```

## Как это работает

- Применённые миграции записываются в таблицу `schema_migrations` (version, name, checksum, applied_at).
  Повторный запуск применяет только новые файлы.
- Каждая миграция выполняется в отдельной транзакции вместе с записью в `schema_migrations`.
  Если SQL упал, не применится ни миграция, ни отметка о ней.
- Для каждого файла считается контрольная сумма sha256 (без учёта CRLF/LF, чтобы Windows и Linux совпадали).
  Если уже применённый файл изменили, `migrate` остановится с ошибкой. Применённые миграции не редактируют:
  любое изменение схемы оформляется новой миграцией.
- На время работы берётся `pg_advisory_lock`, поэтому два одновременных запуска (например, два инстанса
  сервера при деплое) не применят одну миграцию дважды.

## Новая база (локально или новый проект Supabase)

1. Прописать `DATABASE_URL` в `backend/.env`.
2. `npm run migrate`.

## Существующая база (текущий Supabase)

Таблицы там уже есть. Все `CREATE` в 0001 написаны с `IF NOT EXISTS`, а индексы в 0002 тоже
`IF NOT EXISTS`, поэтому `npm run migrate` безопасен: существующие таблицы и данные не трогаются,
добавятся только недостающие индексы.

Перед первым запуском на рабочей базе:

1. Сделать резервную копию (Supabase → Database → Backups или `pg_dump`).
2. Проверить, что нет пользователей, у которых email или username отличаются только регистром.
   Иначе уникальные индексы из 0002 не создадутся, и миграция откатится целиком:
   ```sql
   SELECT lower(email), count(*) FROM users GROUP BY 1 HAVING count(*) > 1;
   SELECT lower(username), count(*) FROM users GROUP BY 1 HAVING count(*) > 1;
   ```
3. Сравнить схему с файлами. Типы колонок восстановлены по коду сервера, а реальная база могла
   создаваться вручную и отличаться (например, `serial` вместо identity или `timestamp` без зоны).
   ```bash
   pg_dump --schema-only --no-owner "$DATABASE_URL" > schema-actual.sql
   ```
   Если отличия есть и важны, стоит поправить `0001` под реальную базу до первого применения.

Если индексы и всё остальное уже созданы вручную, можно просто отметить миграции применёнными:
`npm run migrate:baseline -- 0002`.

## Как добавить изменение схемы

```bash
npm run migrate:new -- add_track_mood
# написать SQL в migrations/0003_add_track_mood.sql
npm run migrate
```

Внутри файла можно писать несколько команд. Не используйте `CREATE INDEX CONCURRENTLY`:
оно не работает внутри транзакции.
